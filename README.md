# gaisan

GitHub Pages でそのまま公開できる、個人ホームページ用の静的サイトです。

## 構成

- `index.html`: ページ本体
- `entry.html`: 各アイデアや項目の詳細ページ
- `styles.css`: レイアウトとデザイン
- `content.js`: 掲載する内容
- `catalog.js`: 作品一覧用の分類・サムネイル・リンク表示の共通処理
- `script.js`: 作品一覧・絞り込み・制作メモ・更新履歴を描画
- `entry.js`: 詳細ページを描画

## GitHub Pages で公開

1. GitHub のリポジトリ設定で `Pages` を開く
2. `Build and deployment` の `Source` を `Deploy from a branch` にする
3. Branch を `main` / `/ (root)` に設定して保存
4. 数分待つと `https://kamibukuro18.github.io/gaisan/` で公開される

## 更新方法

基本は `content.js` を更新すれば十分です。

- `featured`: 既存のプロフィール・リポジトリリンクデータ（現在のトップおすすめ作品は `script.js` の `selected` で指定）
- `games` / `aiGames`: ゲームなどの公開作品
- `projects`: アプリ・ツール・サイト制作など
- `models3d`: BOOTHなどで紹介・販売している3D作品
- `ideas`: アイデア
- `notes`: 短いメモ
- `timeline`: 更新ログ

公開更新時は、公開済みの変更内容を `timeline` にも同時に追記します。公開前の作業は完了扱いで記録せず、公開確認後に更新ログへ追加します。

詳細ページを持たせたい項目には `slug` と `page` を追加します。現在の作品カードは、`catalogHref` があればそのURL、なければ `slug` から `entry.html?type=...&slug=...` へリンクします。`href` は販売・プレイなどの主な外部／公開先への導線です。

各要素は次の形で追加できます。

```js
{
  slug: "sample-entry",
  meta: "Project",
  title: "repo name",
  summary: "短い説明",
  cta: "Read detail",
  year: "2026",
  tags: ["Web", "Demo"],
  page: {
    eyebrow: "Project / 2026",
    intro: "詳細ページの導入文",
    highlights: ["要点1", "要点2"],
    sections: [
      {
        title: "概要",
        paragraphs: ["ここに説明を書く"],
        bullets: ["箇条書きも追加できる"]
      }
    ]
  }
}
```

今後、アイデアやリンクを投げてもらえれば、この構成に合わせてこちらで整えて追加できます。

## 3Dモデルカタログの保守

- `models.html` / `models.css` / `models.js`: 1ページの全件一覧、検索、カテゴリ絞り込み。
- `assets/models/index.json`: M300-001〜M300-103の103件のみ。名称・タグ・用途の要約・注意は、保存済みモデルの実READMEを確認して手編集します。未完成の104以降や、同じモデルの別姿勢を追加件数に含めません。
- `assets/models/previews/`: 各モデル1枚、計103枚のWebPプレビュー。モデル原本、非公開の検証ログ・制作資料、認証情報は公開しません。カタログ掲載はダウンロード提供や公開ライセンスの設定ではありません。

Python 3とPillowがある環境で、公開データと画像を検証します。

```bash
python scripts/build-model-catalog.py
```

既存hero画像からサムネイルを作り直す場合のみ、非公開の正規化済みソース一式をリポジトリの**外**へ置き、`--source /path/to/private-normalized-bundle` を指定します。スクリプトは元画像のハッシュと形式を確認し、既存heroを最大640pxのWebPへ再圧縮します。モデル生成・変更・再レンダーは行いません。ソース一式や元README／manifestをこの公開リポジトリへコミットしないでください。

```bash
node --test tests/models-search.test.cjs
node --check models.js
python -m http.server 8000
```

上の静的サーバーを起動したまま、PlaywrightとChromiumが利用できる別ターミナルで実画面テストを実行します。Chromiumの場所が異なる場合は`CHROMIUM_PATH`を指定します。

```bash
node tests/models-browser.cjs http://127.0.0.1:8000/
```

ブラウザテストの画像は既定で`/tmp/gaisan-model-catalog-qa`へ保存され、公開ファイルには含めません。更新ログは既存方針どおり、公開反映を確認してから追記します。

## 更新の方向性と引き継ぎ

このサイトは「GAIさんの記録場所」であり、作ったものを見てもらい、実際に遊ぶ・使う・購入する場所へつなぐポートフォリオです。ゲーム、アプリ・ツール、3Dモデルに加え、動画やサイトサンプルも掲載対象として育てていきます。アイデア・メモ・過去の更新履歴も残します。

### 維持する方向性

- 現在の作品棚、カテゴリ絞り込み、詳細ページを基本に、作品が増えても探しやすい構成を維持します。
- シンプルでミニマルなダークテーマを基本とし、作品そのものが主役になる見せ方にします。サイト本体の案内と、個々の実験的な作品の表現は分けて考えます。
- 一覧には短い説明と作品を識別できる画像、詳細ページには背景・特徴・使い方・注意点を載せます。サイト制作の作品は、何を意図して作ったかも説明します。
- 制作中・公開中・販売中を混同せず、実際に確認できた状態を記載します。未確認の機能・互換性・実績を補って書きません。
- 既存の作品データ、詳細URL、制作メモ、履歴を保ちます。外部の正式公開先へ移った作品はリンクと画像を更新し、古い試作版へ誘導しないようにします。
- GitHub Pagesで動く静的構成を維持します。大きな構成変更や新しい運用基盤への移行は、通常の作品追加とは分けて検討します。

### 作品・商品を追加するとき

1. 対象作品の正式な名前、説明、現在の公開先を確認します。BOOTH商品は指定された商品ページと照合し、仕様・収録物・利用上の注意を取り違えないようにします。
2. `content.js` の該当配列に追加します。既存作品の更新は同じ `slug` を使い、重複登録を避けます。
   - ゲームは `games` / `aiGames`、アプリ・ツールやサイト制作は `projects`、販売3D作品は `models3d` を基本とします。既存項目は不用意に別配列へ移しません。
   - 一覧の分類は `category` で指定できます。現在の絞り込み値は `game`、`tool`、`video`、`web`、`3d`、`site` です。サイト制作には `category: "site"` を使います。動画専用の配列を追加するだけでは表示されないため、現行の `catalog.js` の集約対象に合わせます。
   - `title`、`summary`、`year`、`tags`、必要に応じて `status` を設定し、`page.intro`、`page.highlights`、`page.sections` に詳細を記載します。
3. `cover` を一覧・詳細の代表画像に設定し、追加画像は `page.gallery` または `gallery` の `{ src, alt, caption }` で登録します。詳細の代表画像の説明は `page.heroAlt` に書けます。
   - 現行の一覧描画では `cover` だけでなく、`catalog.js` の `styles[slug]` に `visual: "image"` を設定する必要があります。必要な `caption` と `source` も設定し、3D以外の画像にBOOTH由来と誤表示しないようにします。
   - 画像は該当作品の公式商品画像、実際のゲーム／アプリ／サイトの画面、または使用を認められた作品素材を使います。別作品の画像で代用しません。出典・取得方法は [THUMBNAIL_SOURCES.md](THUMBNAIL_SOURCES.md) に残します。
   - 公式ページが開けない場合は、確認できた範囲と不足を区別します。コンセプト画像を使う場合も実画面と混同させません。
4. `href` に主な販売・プレイ・利用先を設定し、関連リポジトリや追加リンクは `page.sections[].links` に `{ label, href }` で載せます。カードから詳細へ、詳細から利用先へ実際に移動できることを確認します。
5. 公開対象の画像だけを適切なサイズで `assets/` に置きます。モデル原本、非公開制作資料、認証情報を紹介ページの追加に紛れて公開しないようにします。

### 公開・確認・更新履歴

- 変更前に最新のREADME、[rules.md](rules.md)、対象データを確認します。上の運用手順は技術的な引き継ぎであり、未依頼の作品公開やデータ共有の範囲を広げるものではありません。
- 変更したJavaScriptは `node --check content.js` などで構文を確認し、`python -m http.server 8000` などの静的サーバーで表示を確認します。3D検索カタログを変更した場合は上記の専用テストも実施します。
- PC・スマートフォン幅で、一覧画像、カテゴリ絞り込み、詳細ページの画像・説明、戻る導線、販売／プレイ先を確認します。必要に応じてHTML内のCSS・JSのバージョン指定も更新します。
- リポジトリへの反映とGitHub Pagesへの反映は分けて確認します。コミットできただけで公開済みとは扱わず、公開URLに変更が出たことを確認します。
- サイト更新と更新履歴は一組で扱います。公開確認後、`content.js` の `timeline` の先頭へ `date`、`title`、`summary` を追記し、その履歴自体の公開反映も確認します。未公開の予定・作業途中を完了として記録しません。
- 完了報告には公開URLと変更点を添えます。テスト未実施、リンク先の閲覧不能、公開待ちがあれば、その状態を明記します。

### 3D作品紹介と検索カタログの区別

`models3d` は販売・紹介ページへの入口、`models.html` は保存済み制作モデルを名前・ID・タグなどで探すための一覧です。両者を同一の件数や公開範囲として扱いません。

現行カタログはM300-001〜103の103件です。追加する場合は、保存済み実モデルの完成状態・README・プレビュー・公開してよい情報を確認し、検証スクリプトや件数表記も含めて変更範囲を整理します。カタログへの掲載を、モデル原本の配布やライセンス付与とみなしません。
